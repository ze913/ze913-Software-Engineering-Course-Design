## 一、项目章程（Charter）

### 1. 立项背景：为谁解决什么痛点

- 目标用户：本校本科生——物品在教室、图书馆、食堂、操场高频遗落，捡到东西的人想还却找不到失主
- 核心痛点：
  1. 失物信息散落在 QQ 群/表白墙/朋友圈，无集中发布与检索渠道；
  2. 认领无凭证流程，冒领纠纷频发，失主与拾获者缺乏可信对接；
- 一句话业务目标（可衡量）：**让用户 1 分钟内完成一条失物/招领信息的发布或检索，认领过程全程留痕可追溯**
- 调研证据：见 docs/01-需求调研报告.md（真人访谈 + 问卷，立项后一周内完成）

### 2. 边界：做什么、不做什么

| 做（按增量） | 不做（人工兜底/后置） |
|---|---|
| v0.1 游客浏览/搜索 + 注册登录 + 发布/编辑/下架失物 | 图片上传（用文字描述代替） |
| v0.2 认领申请与审核 + 管理员审核 + 邮件通知 + RBAC | 即时聊天（认领沟通线下/站内留言兜底） |
| v0.3 平台统计 + 部署 + 可用性监控（加分） | 在线支付、第三方登录（OAuth）、找回密码（人工兜底）、AI 图像识别 |

### 3. 干系人

| 干系人 | 系统角色 | 说明 |
|---|---|---|
| 在校学生（失主/拾获者） | USER | 发布、编辑、认领、收藏 |
| 访客 | GUEST | 仅浏览与搜索（三角色之一，权限控制） |
| 平台管理员 | ADMIN | 物品/认领审核、分类与用户管理 |
| 维护方/部署者 | —（非系统角色，仅干系人维度） | 部署、监控、数据备份；单人全流程中由本人兼任 |

> 版本 2 硬性要求：≥3 种用户角色 + 权限控制 + ≥1 个外部集成点（第三方登录/支付/地图/消息推送其一）。
> **本项目：GUEST/USER/ADMIN 三角色 + RBAC；集成点 = 邮件通知（SMTP，`spring-boot-starter-mail`）**——无资质门槛，QQ/163 邮箱即可演示，认领结果与物品被认领时自动提醒失主。

### 4. 过程模型选型论证

**选择：增量模型 + 轻量敏捷实践（Issue 驱动、短迭代、每迭代回顾）**

理由（结合本项目特点）：
1. 课程硬性要求 ≥3 个可交付增量（v0.1/v0.2/v0.3），增量模型天然匹配——每个增量都有可运行、可演示的版本，答辩现场永远有一个能跑的系统；
2. 需求在 8 周内会随调研/评审演进，增量 + 每轮迭代回顾提供正式的变更吸收点，避免瀑布式"最后才知道对不对"；
3. 单人全流程下，短迭代（1–2 周）比螺旋/UP 更轻量可控，仪式感（计划-构造-测试-评审）由 Issue/PR 机制制度性保证；
4. 不选纯瀑布：课程要求两轮以上迭代与持续集成，瀑布无法满足；不选 UP：单人无法支撑其文档体量。

### 5. 技术选型论证

| 选型 | 理由 |
|---|---|
| Java 17 + Spring Boot 4 | 课程先修 Java；Boot 生态成熟，webmvc + 自动配置；17 为 LTS |
| MyBatis + MySQL | SQL 可控、便于课程讲解数据库设计；MySQL 与数据库课程衔接 |
| JavaMail（SMTP） | 外部集成点（消息推送），零资质门槛，风险最低的合规集成方式 |
| H2（测试）+ GitHub Actions | 测试无需外部数据库，CI 每次 push 全自动跑测试，红灯禁止合并 |
| Mermaid（模型源文件） | 图表即代码、随仓库版本化、可评审 diff，符合"每张图一个 PR" |
| 部署目标 | jar 本地/服务器部署 + Actions 构建发布（v0.3 尝试自动化部署与监控） |

### 6. 里程碑与迭代计划

| Milestone | 迭代 | 内容 | Release |
|---|---|---|---|
| v0.1 | 迭代 1 | 游客浏览/搜索 + 注册登录 + 发布/编辑/下架（单用户闭环） | v0.1 |
| v0.2 | 迭代 2 | 认领流程（申请-审核-确认归还）+ 管理员审核 + RBAC + 邮件通知 | v0.2 |
| v0.3 | 迭代 3 | 平台统计 + 部署上线 + 可用性监控（加分） | v0.3 |

> 要求 ≥2 轮"计划-构造-测试-评审"迭代，本计划 3 轮；每轮开/关一个迭代 Issue（iteration 模板），回顾留痕。

### 7. 规模达标自查（版本 2 硬性指标）

- [ ] ≥3 个可交付增量（v0.1 / v0.2 / v0.3）
- [ ] ≥20 个用例（计划 23 条用户故事 = 20 功能 + 3 非功能）
- [ ] ≥15 个分析类
- [ ] ≥1 个技术风险点登记并管理（**已识别：邮件服务可达性**，备选 Server酱 推送，technical-risk Issue 跟踪）
- [ ] ≥3 种用户角色 + 权限控制（GUEST/USER/ADMIN + RBAC）
- [ ] ≥1 个外部集成点（邮件通知 SMTP）
- [ ] 单元测试（核心模块覆盖率声明）+ 集成测试 + 验收测试
- [ ] 抽样代码评审 ≥2 次（review Issue）

## 二、工程约定（DevOps 全流程）

### 1. 分支保护（一次性设置，GitHub → Settings → Branches）

- [ ] 默认分支：`main`（首次推送前执行 `git branch -M main`）
- [ ] 开启：Require a pull request before merging（**1 个审批**）
- [ ] 开启：Require status checks to pass → 勾选 `CI / Maven 构建与测试 (JDK 17)`
- [ ] 禁止直推 main：所有变更走 feature 分支 + PR

> 单人全流程的评审机制见 [docs/00-个人全流程工作方案.md](docs/00-个人全流程工作方案.md)。

### 2. 工作流（一条需求的生命周期）

```
调研证据 → 用户故事 Issue(story 标签) → SRS/模型文档 PR
        → 开发分支 + 代码 PR(Closes #N) → CI 绿 + 评审签字 → 合并
        → 测试用例(引用 #N) → 缺陷 Issue(bug) → 修复 PR → Release 打 tag
```

### 3. Issue / PR / CI 纪律

- 每条用户故事一个 Issue，带 story 标签、验收标准、调研证据、关联里程碑
- 需求变更一律走 change-request 模板（申请-评审-关闭）
- 每个 PR 关联 Issue（`Closes #N`）、附测试证据与 AI 使用声明
- push 自动跑 CI；**红灯禁止合并**（分支保护强制）
- 每个增量打 tag：`git tag -a v0.1 -m "..."` → 自动构建 jar 并发布 Release
- 提交纪律：小步提交、分散到全周期；禁止"最后一晚打包上传"

### 4. 标签体系

由 `.github/labels.yml` 自动同步：`story` / `non-functional` / `change-request` / `bug` / `technical-risk` / `ai-usage` / `review` / `iteration` / `documentation` / `design` / `question`

## 四、本地开发

```bash
# 依赖：JDK 17+、Maven 3.9+、MySQL 8（本地开发库）
mysql -uroot -e "CREATE DATABASE lostfound DEFAULT CHARSET utf8mb4;"

# 启动（先用 db/schema.sql 建表）
mvn spring-boot:run

# 测试（H2 内存库，无需 MySQL）
mvn test
```

环境变量（部署时注入，密钥不入库）：`DB_URL` / `DB_USERNAME` / `DB_PASSWORD` / `MAIL_*`（邮件 SMTP 配置）
