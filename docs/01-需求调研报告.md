# 需求调研报告：校园失物招领平台（LostFound）

> 版本：v1.0 ｜ 作者：需求分析师 ｜ 评审状态：待评审 ｜ 对应检查点：第 2 课（调研报告 PR 合并）
> 调研周期：2026-11-19 ～ 2026-11-26
> 原始材料：`需求调研/问卷数据.pdf`（问卷《校园失物招领情况小调查》汇总导出）

## 1. 调研概况

| 项目 | 内容 |
|---|---|
| 调研目的 | 验证"校园失物信息分散、找回率低、认领无凭证"三个立项假设是否成立，并据此收缩需求范围 |
| 主要方法 | 线上问卷（结构化封闭题为主） |
| 辅助方法 | 竞品与现有渠道的桌面研究（QQ 群、表白墙、校园贴吧、二手平台） |
| 样本量 | 20 份有效问卷（本科生 17 人 / 85%，研究生 3 人 / 15%） |
| 样本覆盖 | 本校在校学生，均有过或目睹过校园物品遗失经历 |
| 数据形态 | 汇总统计表（各题小计 + 比例），**未拿到逐份原始答卷** |

## 2. 调研方法

**问卷设计思路**：按"经历 → 现有做法 → 顾虑 → 期望功能"四段递进，避免直接问"你要什么功能"（那样得到的是药名，不是病名）。共 8 题，7 道封闭题 + 1 道开放题，填写耗时控制在 90 秒内，降低中途放弃率。

**现有渠道的桌面研究（定性）**：

| 渠道 | 现状 | 结构性缺陷 |
|---|---|---|
| 班级/课程群 | 触达同班同学，但只覆盖熟人圈 | 无检索、无归档，消息 24 小时内被刷走 |
| 表白墙/校园墙/朋友圈 | 曝光量大，是当前第一渠道（75%） | 靠人工翻历史动态，无结构、无法按地点筛 |
| 食堂/教学楼公告栏 | 线下可见（65%） | 需人到现场，跨校区/跨楼栋完全失效 |
| 直接回原地找 | 40% 的人首选 | 无第三方见证，东西被别人捡走后无提示 |
| 校园贴吧/二手平台 | 存在零散帖子 | 非失物场景专用，分类与状态管理缺失 |

结论：**不缺"发布的地方"，缺"能按地点/分类检索、且认领有凭证的地方"**。这句话是后面所有需求的取舍依据。

## 3. 干系人识别

按"使用 / 管理 / 维护 / 付费 / 监管"五个维度逐个过，避免只盯着学生用户。

| # | 干系人 | 维度 | 在系统中的角色 | 关注点 | 对应需求草案 |
|---|---|---|---|---|---|
| S1 | 失主（在校学生） | 使用、付费（时间成本） | USER | 快速找到、确认不是冒领、有结果通知 | REQ-02、REQ-05、REQ-07 |
| S2 | 拾获者（在校学生） | 使用 | USER | 低成本的"上报"路径、不被纠缠 | REQ-01、REQ-03 |
| S3 | 游客（未登录浏览者） | 使用 | GUEST | 不注册也能看，避免被强制登录挡在门外 | REQ-04 |
| S4 | 平台管理员 | 管理 | ADMIN | 审核认领申请、分类维护、处理纠纷 | REQ-06、REQ-09 |
| S5 | 教学楼/宿舍楼管、失物招领处老师 | 使用（线下兜底） | 非系统角色，仅干系人 | 线下代收的物品如何登记、如何被学生查到 | REQ-03（线下点信息展示） |
| S6 | 辅导员/学院学工 | 管理、监管 | 非系统角色 | 冒领纠纷的处置依据、平台数据的合规性 | REQ-08（留痕可导出） |
| S7 | 系统维护/部署者（本人兼任） | 维护 | 非系统角色 | 部署、备份、邮件服务可达性 | NFR-03、技术风险 R-01 |
| S8 | 学校信息化主管部门 | 监管 | 非系统角色 | 学生个人信息最小化采集、不对外泄露 | NFR-02 |

**关键取舍**：S5、S6、S8 不做成系统角色，只作为需求约束来源。理由是线下失物招领处没有对接接口，强做"楼管后台"会超出课程周期；但他们的存在改变了两个设计——①招领信息要能被"代发"（管理员代录），②平台必须保留完整认领留痕，供学工处置纠纷时调取。

## 4. 业务目标

**一句话（可衡量）**：让本校学生在 **2 分钟内** 通过地点/分类检索定位到自己遗失物品的线索，并让每一次认领都经过"申请—审核—归还确认"三段留痕。

目标拆成三个可验证指标：

| 指标 | 基线（调研现状） | 目标 | 验证方式 |
|---|---|---|---|
| 检索耗时 | 靠翻表白墙历史动态，无量化基线，主观"要翻很久" | 单次检索 ≤ 2 分钟（关键词 + 地点 + 分类筛选） | 验收测试计时用例 |
| 找回率 | 45% 的人"很少找回"或"从没找回"（9/20） | 平台内物品状态从"待认领"流转到"已归还"的比例 ≥ 60%（运营指标，答辩演示阶段观察） | 平台统计页 |
| 认领凭证覆盖率 | 现状无任何凭证，靠口头约定 | 100% 的归还动作经过认领申请 + 管理员审核 + 归还确认三步 | 状态机与数据表留痕 |

## 5. 现状痛点与调研证据

每条痛点都必须指到具体题号与人数，不接受"我觉得""很多人都这样"。

| # | 痛点 | 调研证据（题号 / 人数 / 比例） | 影响谁 | 严重度 |
|---|---|---|---|---|
| P1 | 遗失是高频事件，不是偶发 | 第2题：丢过 3–5 次 12 人（60%），1–2 次 7 人（35%），**至少丢过 1 次共 19 人（95%）** | 全体学生 | 高 |
| P2 | 找回率显著偏低 | 第3题："很少找回"8 人（40%）+ "从没找回"1 人（5%）= **45%**；"基本都找回"仅 1 人（5%）；"找回一半以上"10 人（50%） | 失主 | 高（核心痛点） |
| P3 | 信息渠道分散，无统一入口 | 第4题：表白墙/校园墙/朋友圈 15 人（75%）、食堂教学楼公告栏 13 人（65%）、班级课程群 5 人（25%）、直接回原地找 8 人（40%）——**四个渠道并行，没有一个被多数人单独依赖** | 失主 + 拾获者 | 高 |
| P4 | 拾获者侧处理路径断层：捡到后没有"下一步" | 第5题："带回后不知如何处理" 12 人（**60%**）；"发群/表白墙/校园找失主" 13 人（65%）；"原地等待或交给楼管" 8 人（40%） | 拾获者 | 高（立项时遗漏） |
| P5 | 冒领顾虑普遍存在 | 第6题："很担心" 8 人（40%）+ "有点担心" 10 人（50%）= **90%** 存在顾虑；"没想过" 仅 2 人（10%） | 失主 + 拾获者 | 高 |
| P6 | 现有渠道无法做结构化检索 | 第7题："按地点/分类搜索" 16 人（**80%**），与"认领在线申请与审核"并列第一 | 失主 | 高 |
| P7 | 认领流程缺凭证、缺反馈 | 第7题："认领在线申请与审核" 16 人（80%）、"认领结果通知" 11 人（55%） | 失主 + 拾获者 | 高 |
| P8 | 发布动作本身不是强需求 | 第7题："发布失物招领信息" 仅 9 人（**45%**），低于搜索 35 个百分点 | 平台供给侧 | 中（风险项，见 §5 意外 1） |

**由证据直接导出的需求优先级（MoSCoW）**：

| 优先级 | 需求 | 证据来源 | 增量归属 |
|---|---|---|---|
| Must | 按地点 + 分类 + 关键词检索（游客可用） | P3、P6（80%） | v0.1 |
| Must | 失物/招领信息发布、编辑、下架 | P1、P4 | v0.1 |
| Must | 注册登录 + 三角色 RBAC | 版本2 硬性要求 | v0.1 |
| Must | 认领在线申请 + 管理员审核 + 归还确认（状态机留痕） | P5、P7（80%） | v0.2 |
| Must | 认领结果邮件通知 | P7（55%） | v0.2 |
| Should | 管理员代录（线下招领点物品） | P4（60%）、S5 | v0.2 |
| Should | 平台统计（待认领/已归还/超时未领） | 目标指标 2、答辩演示 | v0.3 |
| Could | 收藏/订阅关注物品 | 问卷未测，低优先 | v0.3 视工期 |
| Won't | 平台信用分/黑名单 | 仅 15%，见 §5 意外 2 | 明确不做 |

## 6. 意外发现与被否掉的想法

真实调研的价值在反直觉处。以下三条都不是立项时的预期，且**前两条直接修改了原始设计**。

**意外 1：用户更想"找"，不想"发"，平台存在供给侧冷启动风险。**
"按地点/分类搜索"与"认领申请审核"各 80%，而"发布失物招领信息"只有 45%。结合第5题——65% 的拾获者会发到群里或表白墙（已经解决了一部分发布需求），可以推断：**用户把发布动作留在了熟悉的社交渠道，只在"找"的时候才需要一个专门平台。** 这意味着 v0.1 若只做"发布 + 浏览"，很可能上线后内容空空。

对策（已写入设计约束）：
1. 发布成本压到最低——必填字段控制在 4 个（物品名、地点、时间、分类），描述选填；
2. 给管理员/楼管提供代录入口，先由运营侧注入种子内容；
3. 招领信息与线下公告栏信息在页面并列展示，让"只信任公告栏"的 65% 人群也能被覆盖。

**意外 2：90% 担心冒领，但只有 15% 想要"平台信用记录"——担心的是"这一次"，不是"这个人"。**
立项时把"冒领纠纷"写成了核心痛点，顺势想加信用分体系。数据否掉了这个方向：用户要的是一次认领的可核验凭证（谁申请、管理员是否核过、何时归还），而不是一套长期信用档案。信用分还会带来评分规则、申诉通道、冷启动无数据等一连串工作量。

**被否掉的设计：平台信用分 / 黑名单 / 实名学号绑定。** 理由：诉求强度不足（15%），且实名绑定涉及个人信息采集，触碰课程"数据合规、隐私最小化"的风险红线（对应 NFR-02）。

**意外 3：拾获者侧有 60% 的人"捡到后不知怎么办"，这是立项时完全没写的痛点。**
原章程的痛点描述偏失主视角（"找不到信息"），但数据显示拾获者同样卡住：愿意还，但不知道该交给谁、要不要等、等多久。这解释了为什么 40% 的人选择"原地等待或交给楼管"——不是首选方案，是没有更好方案。

对策：v0.2 增加"招领快速上报"（比失物发布更短的路径）+ 展示线下代收点（各楼栋楼管处、失物招领处位置与开放时间）。后者只做信息展示，**不做线下代收点的后台管理**，明确划在边界外。

**其他被否掉的想法**：

| 想法 | 否决理由 |
|---|---|
| 图片上传 | 立项已划为不做；问卷也未测，无证据支持；图片存储与合规成本高于收益 |
| 站内即时聊天 | 认领沟通可由"申请附言 + 管理员审核 + 线下当面交付"覆盖，聊天会引出消息未读、拉黑、骚扰治理 |
| 第三方登录（微信/QQ） | 外部集成点已选定邮件（零资质、可控），再加 OAuth 会引入学校资质与审核周期风险 |
| AI 图像识别匹配失物 | 20 份样本中无人提及；课程明确"不强行堆砌 AI"；且答辩讲不清技术细节反而扣分 |
| 找回密码自助流程 | 单人项目，邮箱验证链路易失败，改人工兜底（联系管理员重置），成本更低、风险可控 |

## 7. 需求条目草案（供 SRS 与用户故事 Issue 使用）

以下 8 条为从证据直接落地的用户故事草案，三段式 + Given/When/Then，供第 3 课 Issue 化时扩到 20 条以上（含 ≥3 条非功能）。

**REQ-01（P1/P4｜v0.1）** 作为拾获者，我想用不超过 4 个必填字段发布一条招领信息，以便我在 1 分钟内把捡到的东西挂上去。
Given 我已登录且身份为 USER，When 我填写物品名、地点、时间、分类并提交，Then 系统在 2 秒内生成一条状态为"待认领"的招领记录并返回详情页。

**REQ-02（P3/P6｜v0.1）** 作为失主，我想按地点、分类、关键词组合筛选，以便我不必翻遍历史动态就能定位线索。
Given 平台已有 ≥10 条记录，When 我选择"教学楼 + 电子设备"并输入关键词，Then 列表仅显示同时命中的记录，且响应时间 ≤ 2 秒。

**REQ-03（P4｜v0.2）** 作为拾获者，我想看到校内线下代收点的位置与开放时间，以便我把物品交给最近的楼管处。
Given 我在招领详情页，When 我点击"线下上交"，Then 页面展示可代收点名称、楼栋、开放时段，且不要求我注册额外账号。

**REQ-04（S3｜v0.1）** 作为游客，我想在不登录的情况下浏览与搜索，以便我先确认值不值得注册。
Given 我未登录，When 我访问首页并执行搜索，Then 我能看到列表与摘要信息，但发布、申请认领时被引导至登录页。

**REQ-05（P5/P7｜v0.2）** 作为失主，我想对某条招领记录提交认领申请并附特征描述，以便拾获者/管理员能核验我是不是真失主。
Given 记录状态为"待认领"，When 我提交含物品特征描述的申请，Then 记录状态变为"认领待审"，且我在个人中心能看到申请时间与审核状态。

**REQ-06（P5/P7｜v0.2）** 作为管理员，我想审核认领申请（通过/驳回并填理由），以便冒领在归还前被拦下。
Given 存在"认领待审"申请，When 我点击通过，Then 记录状态变为"待归还"，申请人收到邮件通知，驳回时理由必填且通知申请人。

**REQ-07（P7｜v0.2）** 作为失主，我想在归还完成后收到邮件通知，以便我知道流程已经闭环。
Given 管理员确认归还，When 状态流转为"已归还"，Then 申请人与其对应记录在 1 分钟内收到一封含物品名与归还时间的邮件。

**REQ-08（S6｜v0.3）** 作为管理员，我想导出某条记录的完整流转日志，以便学工处置冒领纠纷时有据可查。
Given 我以 ADMIN 登录，When 我导出指定记录的日志，Then 输出含每次状态变更的时间、操作人、理由的清单。

**非功能草案（对应版本2 的 ≥3 条要求）**：

- NFR-01 性能：Given 200 并发同时提交检索请求，When 持续 1 分钟，Then 95% 请求 2 秒内返回。
- NFR-02 安全：Given 用户密码入库，When 查询数据库，Then 密码为不可逆哈希；学号/手机号等个人信息仅在必要字段采集。
- NFR-03 可用性：Given 邮件服务不可达，When 发送通知失败，Then 核心业务（发布/审核/归还）不阻断，失败进入重试队列并记录（对应技术风险 R-01）。

## 8. 调研结论

1. **核心痛点被证实，但重心需要调整**：立项写的是"信息分散 + 冒领纠纷"，数据显示更痛的是"检索能力缺失（80%）"和"捡到后无处安放（60%）"。产品重心从"发布墙"改为"可检索的失物索引 + 有凭证的认领流程"。
2. **边界进一步收窄**：图片、聊天、第三方登录、信用分、AI 识别全部移出范围，换来 v0.1 一个真能跑起来的检索闭环。
3. **最大风险不是技术，是内容供给**：45% 的发布意愿 × 小样本校园环境，冷启动需靠管理员代录与线下联动，这条已登记为迭代 1 的运营风险。
