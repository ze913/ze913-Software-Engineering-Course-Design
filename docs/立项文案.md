# 立项文案

## 一句话

**校园失物招领平台（LostFound）**：让本校学生 1 分钟内完成一条失物/招领信息的发布或检索，认领过程全程留痕可追溯。

## 按选题六原则陈述

**1. 价值真实**——为谁解决什么痛点
- 目标用户：本校本科生。物品在教室、图书馆、食堂、操场高频遗落，捡到东西的人想还却找不到失主。
- 痛点：失物信息散落在 QQ 群/表白墙/朋友圈，无集中发布与检索渠道；认领无凭证流程，冒领纠纷频发，失主与拾获者缺乏可信对接。（调研证据：访谈 + 问卷，立项后一周内完成并入库）

**2. 边界清晰**——做什么、不做什么
- 做：失物/招领信息的发布、搜索、认领申请与审核、邮件通知、平台统计。
- 不做：图片上传（文字描述代替）、即时聊天、在线支付、第三方登录、找回密码（人工兜底）、AI 图像识别。

**3. 难度适配**——量力而行，不堆砌 AI
- 技术栈：Java 17 + Spring Boot + MyBatis + MySQL，均为课程先修内容；核心难点仅为认领审核状态机，可在课程周期内高质量完成且答辩讲得清。

**4. 可验证**——有明确验收标准
- 23 条用户故事（20 功能 + 3 非功能），每条带 Given/When/Then 验收标准；3 个增量各有可运行版本与 GitHub Release；CI 每次提交自动跑测试。

**5. 风险可控**——数据合规、后果可承受
- 不涉及金钱交易与高危数据；已识别技术风险 1 项：邮件服务可达性（缓解方案：SMTP 双通道 + Server酱 备用推送），以 technical-risk Issue 登记跟踪。

**6. 愿意投入**——场景真实、可持续迭代
- 选题来自自身校园生活，需求反馈触手可得，便于持续改进。

## 规模与形式

| 指标 | 承诺值 |
|---|---|
| 用户故事 | 23 条（20 功能 + 3 非功能：性能/安全/可用性） |
| 用户角色 | 3 个（游客/用户/管理员）+ 权限控制 |
| 外部集成点 | 1 个（邮件通知，SMTP） |
| 增量/迭代 | 3 个增量（v0.1/v0.2/v0.3）+ 3 轮迭代 |
| 过程形式 | 个人全流程（加分项）：一人分饰多角色，评审按 docs/00 方案留痕 |
